# 地图与餐饮准确性续测

日期：2026-10-15。分支：`codex/map-food-accuracy`。续测基线：`56a769d5`。

**最终交付更新：** 本文保留当轮失败和限制；后续修复与最新证据见[交付报告](map-food-accuracy-delivery.md)。

**结论：仍有问题，整体准确性验收尚未通过。** 本轮修复了门店身份合并和 Edge 字段校验的新增遗漏；地图渲染坐标契约与存量内容刷新仍需修复。没有部署服务、发布 App 或修改用户历史数据。

## 已复现并修复

1. **相邻同名分店串用资料。** 原匹配规则可能把同一平台的两个真实门店 ID 合并，即使它们只是共用品牌名、商场地址和客服电话。现在只有相同的真实平台身份才允许同平台合并：Amap 使用 `amap_id`，Foursquare 使用 `fsq_id`。不同真实 ID 保持独立，不转移评分。MapKit 的名称与坐标哈希、缺失上游 ID 的 Amap 哈希仍属于合成 ID，不能当作真实门店身份，否则轻微坐标抖动反而制造重复。Amap 空白 ID 也改走名称与坐标回退，避免所有空串生成同一 ID。
2. **异常 AI 字段进入响应与缓存。** 实际 Edge handler 原先接受负时长、颠倒的时长范围、27 点、25 分、非文本步骤和空白标题。现在校验小时、正整数时长及上下限、0–10 分有限评分、步骤和必填文案；不合法响应返回 502 且不写缓存，已有坏缓存重新生成。缺省与 `null` 仍保留未知含义。`null` 请求体改为受控 400。此校验只能阻止结构和数值错误，不能证明文案对应真实营业情况。

## 尚未解决

### 地图渲染与搜索的坐标边界（高优先级）

使用独立、无业务数据的 iOS SwiftUI/MapKit 探针，在共享 Primary iPhone 上实际执行了两个公开地点搜索，将搜索原始坐标 R 与当前生产转换器输出 W 同时绘制在同一底图。没有收集 GPS、登录或调用付费模型。

| 地点           | 搜索返回的国家码 | 原始 R `[lon,lat]`       | 当前内部 WGS84 输出 W            | 两数值点的距离 |
| -------------- | ---------------- | ------------------------ | -------------------------------- | -------------- |
| 郝店镇人民政府 | CN               | `[113.759462,31.787312]` | `[113.7535764755,31.7893693647]` | 602.29 m       |
| 香港大会堂     | CN               | `[114.16652,22.279659]`  | `[114.1615340522,22.2823844350]` | 595.91 m       |

**观察事实：** 两次搜索均成功；本次环境底图显示高德品牌；R 与 W 在截图中落在不同位置。香港原计划作为不转换对照，实际返回 `CN`，触发了当前的转换，因此该对照的预期没有成立。空查询被本地拒绝，没有发起第三次网络搜索。

**自动计算：** 上表距离由 CoreLocation 对两个坐标计算，只说明来源/转换结果的差距，不是实测定位误差。主 App 的 Annotation、相机、手势返回坐标仍直接使用通用 `CLLocationCoordinate2D`，没有完整的底图输入/输出边界。

**分析判断：** “搜索结果归一成 WGS84”不足以证明“把 WGS84 直接交给当前底图即可正确显示”。仅凭地理范围或 `isoCountryCode == CN` 也不能推断所有环境的搜索及渲染坐标契约。香港截图尤其暴露了这个假设的局限。本轮没有把未经校准的全局加偏移作为生产修复。

**下一实施边界：** 内部持久化、距离与地理围栏继续使用明确的 WGS84；分别校准搜索输入/输出、底图 Annotation/相机/手势以及导航出口。补充同一公开锚点在不同地图服务环境的对照，确定可验证的适配策略，再接入生产。还需要真实设备的 GPS 与建筑落点核对。不得把本探针视为真机定位或所有城市准确的证明。

### 再次探索丢弃同 ID 的更新资料（中优先级）

代码追踪确认三层丢弃：`MapViewModel.exploreNearby` 的 `onBatch` 先移除已经可见的 ID；`ExperienceRepository.appendGenerated` 跳过已保存 ID；`ExperienceService.appendGenerated` 仅新增数量大于零时 reload。因此上游事实缓存即使失效重新生成，旧卡片仍可能不更新。这是代码路径确认，尚未完成主 App 动态回归。

需增加专用的新增/刷新接口及明确的更新策略，保留用户状态、完成记录、标签、实访、照片和社区评分。直接全量 `update` 会覆盖其中一部分；现有 `adoptingContent` 也不是完整的字段保留策略。没有逐字段观察时间前，可先限定 skeleton 升级，不能把普通重复发现当作有权覆盖所有已评估资料。历史错误资料迁移也仍未执行。
